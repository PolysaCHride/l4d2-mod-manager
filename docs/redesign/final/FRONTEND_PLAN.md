# 前端重构：画面要求 → 实现约束 → 技术路线

> 这份文档回答三件事：**重构后要长什么样、要满足什么行为、用什么技术做**。
> 第三部分是重点，也包含对你原始需求的反向质疑。

---

## 一、画面要求（已经从这轮讨论中固化下来）

### 1.1 布局

四区纵向分区 + 右侧详情，1440×900 为基准，最窄 1100。

```
┌─────────────────────────────────────────────────────────────┐
│ 01 TitleBar  品牌 · 搜索 · 工作区 tab · 游戏状态 · 启动 · 窗控 │ 54
├────┬──────────┬───────────────────────────────┬─────────────┤
│ 02 │ 03       │ 04 MainHeader                 │ 07          │
│ R  │ Filter   │ 05 ActionBar                  │ Inspector   │
│ a  │ Panel    │ 06 ModGrid / 任务视图          │             │
│ i  │          │                               │             │
│ l  │ 68+256   │ flex                          │ 326         │
├────┴──────────┴───────────────────────────────┴─────────────┤
│ 08 StatusBar  就绪 / 扫描中（进度条）/ 异常 · 路径 · 版本      │ 28
└─────────────────────────────────────────────────────────────┘
```

### 1.2 每个区域的唯一职责

| 区 | 职责 | 明确不做 |
|---|---|---|
| 01 | 品牌、全局搜索、工作区切换、启动 | 不放分类、不放状态、不放通知 |
| 02 | 一级分类（全部/角色/特感/武器/地图/其他） | 不放二级物品 |
| 03 | 当前范围的下一层筛选（状态、物品、分组） | 不放搜索、不重复一级分类 |
| 04 | 我在哪（面包屑）+ 我在看什么（标题） | 只读，不可点 |
| 05 | 对结果集的操作（计数、视图、排序、刷新） | 不放状态筛选、不做批量选择 |
| 06 | 内容（网格 / 导入 / 下载 / 设置） | 卡片上不放操作按钮 |
| 07 | 选中项的状态与全部操作 | 未选中时收起 |
| 08 | 后台活动的可见性（扫描）+ 路径 + 版本 | 不重复模组计数与游戏状态 |

### 1.3 视觉与交互规则（已逐条确认）

**颜色**
- 只用 `tokens.css` 的语义变量，组件内不出现裸 hex。
- accent 仅作信号（焦点、选中、进度、启用态），不做大面积背景。
- 启用态卡片：方案 C —— 整卡荧光绿 + 2px 黑描边 + 外圈 1px 光环，文字转黑。

**排他规则**
- 搜索只在 01，状态筛选只在 03。
- 卡片点击 = 选中（只影响 07）；**双击 = 切换启停，双向**。
- 右键菜单取消，全部操作并入 07。
- 别名 = 主标题，原名 = 次标题。
- 「归入合集」仅地图类显示。

**文本规则（Linear / Notes 级克制）**
- 无标语、无提示文字、无次要标签。
- 卡片上不重复分类（分类已在 03 表达）。
- 未启用卡片不加「未启用」徽章（没有徽章本身就是状态）。
- 入库字段写作「入库时间」。

**响应式**
- 1440 / 1280 / 1100 三档，零横向溢出。
- 搜索框左边界 = 主区左边界（`calc(var(--rail-w) + var(--filters-w))`）。
- 1100 时顶栏 tab 只留图标、卡片降两列。

**通知**
- 全部用阻塞弹窗，不做 toast / 通知中心。
- 弹窗族：信息 / 警告 / 错误 / 确认 / 危险确认 / 部分失败 / 进行中。

## 二、实现约束（从现有代码量出来的真实情况）

### 2.1 现有规模

| 模块 | 行数 | 说明 |
|---|---:|---|
| `main_window.py` | 2081 | 主窗口、卡片、网格、Inspector 雏形 |
| `dialogs.py` | 1546 | 6 个对话框 + 委托 |
| `theme.py` | 967 | **含 744 行 QSS** + 自绘像素图 |
| `components.py` | 724 | AppDialog / AppMessageBox / 圆形勾选 |
| `workers.py` | 425 | QThread 工作线程 |
| **UI 合计** | **5887** | |
| `app/core/*` | 4234 | 全部业务逻辑，与 UI 无关 |
| **项目合计** | **10121** | |

关键事实：**业务逻辑 4234 行完全独立于 UI**，这是最大的一张牌。

### 2.2 现有 UI 用的 Qt 特性

| 特性 | 用量 | 迁移难度 |
|---|---|---|
| QSS（样式表） | 744 行 | 中：选择器要改写 |
| 自绘 `paintEvent` | 38 处 | 高：需要重新用 CSS 或 canvas 表达 |
| `QStyledItemDelegate` | 1 处（导入列表勾选框） | 中 |
| `QPropertyAnimation` | 悬停/页面切换 | 低：CSS transition 可直接替代 |
| 无边框 + 半透明 | 已实现 | 需要重做（见下） |
| 异步 | `QThread` + signal | 需要桥接 |

### 2.3 现有交互与新方案的冲突点

以下不是"改样式"，是**行为语义变了**，必须改代码：

| 现有行为 | 新行为 | 影响 |
|---|---|---|
| 单击卡片 = 启用（`MUTEX_CATS`） | 单击 = 选中，双击 = 启停 | `ModCard.mousePressEvent` 全删 |
| 右键 = 上下文菜单 | 全部进 Inspector | `show_card_menu` 全删 |
| 双击 = 切换 `switch` | 双击 = 启停且需要同组确认 | 逻辑要重写 |
| 详情用 `DetailDialog` 弹窗 | Inspector 内联 | `DetailDialog` 废弃 |
| Tab 在页面里 | Tab 在顶栏 | 布局重排 |

### 2.4 性能约束

- 网格现有实现**复用 widget**（`self._cards` 字典），不是每次重建。
- 缩略图有 `_PIX_CACHE` + wiki 图回退 + 渐变占位。
- 大库（数百到上千 mod）滚动必须流畅。

这一条会直接淘汰掉一些"看起来很省事"的技术路线。

### 2.5 分发约束

- PyInstaller 打包，`excludes` 里**明确排除了 QtWebEngine**。
- 当前 PySide6 目录 631 MB（含全部模块）。
- 排除 WebEngine 后的实际分发体积需要实测。

## 三、技术路线分析

先说结论：**你问的是"用哪个"，但真正的分歧不在"用哪个框架"，而在"谁负责绘制"。**

### 路线 A：继续 PySide6，全部原生化

QSS + 自绘 widget，把现有 5887 行逐步改造成新结构。

**优势**
- 零新增依赖，打包体积不变。
- 行为一致性最好：Qt 原生控件处理键盘、焦点、输入法、无障碍、高 DPI。
- 性能可控：现有 widget 复用 + 像素缓存机制直接沿用。
- 团队只需懂 Qt。
- 增量迁移：可以一区一区改，随时可发布。

**劣势**
- QSS 是 CSS 的子集，缺 flexbox/grid。三栏 + 卡片流要靠 `QGridLayout` 手算列数。
- 圆角、阴影、渐变、混合模式能力弱。方案 C 的"外圈光环"用 `QGraphicsDropShadowEffect` 近似，会有性能与保真度损失。
- 744 行 QSS 要重写，且 QSS 调试体验差（无 DevTools，改错静默失效）。
- 动画能力弱：呼吸、进度推进要靠 `QPropertyAnimation`，写起来啰嗦。
- **最致命**：这轮讨论的所有设计产物（HTML 原型、`.css`、`.js` 交互逻辑）**无法复用**，等于翻译一遍。设计改了还要再翻一遍。

**工作量估计**：5887 行中约 70% 要改写 ≈ 4000 行。周期最长，返工风险最高（因为设计还在迭代）。

### 路线 B：PySide6 + QtWebEngine，前端用现有 HTML/CSS/JS

QWebEngineView 承载 UI，Python 通过 QWebChannel 提供数据与命令。

**优势**
- **设计产物 100% 复用**：这轮做的 `demo.html` / `demo.css` / `demo.js` 直接就是产品代码。
- 设计迭代零翻译成本：改 CSS 即改界面，与现在的验证流程完全一致。
- 方案 C 的外圈光环、呼吸点、进度条动画，浏览器原生支持，保真度最高。
- 滚动性能：Chromium 对大列表的处理优于 QWidget 手算布局。
- 现有业务逻辑（4234 行）不动，通过 channel 暴露即可。

**劣势**
- **体积**：QtWebEngine 约 150–200 MB，PyInstaller 打包后分发体积可能翻倍。这是最实在的代价。
- 冷启动变慢约 0.5–1.5 秒。
- 内存占用增加（Chromium 多进程，约 +100–200 MB）。
- 无边框窗口 + 半透明需要重做：`QWebEngineView` 与 `WA_TranslucentBackground` 组合有已知限制，圆角窗口要额外处理。
- 双栈调试：问题可能出在 Python、JS，或两者之间的 channel。
- 输入法（中文）在 WebEngine 里通常没问题，但需要在你的目标环境实测。

**工作量估计**：HTML/CSS/JS 已完成约 60%（demo 即产物），剩余是 QWebChannel 桥接 + 窗口控制 + 打包适配 ≈ 1500–2000 行。**周期最短**。

### 路线 C：换到 Electron / Tauri

**这实际上是在换掉整个应用，不是重构前端。**

**优势**
- 前端体验最好，生态最全。

**劣势**
- Python 业务逻辑（4234 行）要么重写，要么打包成 sidecar 子进程。
- sidecar 方案要处理进程生命周期、崩溃恢复、IPC 序列化、杀毒软件误报。这些是纯新增的复杂度，与"重构前端"无关。
- 打包体积 100 MB+，冷启动更慢。
- 你现在能跑 PySide6 的环境，不一定能跑 Electron（虽然大概率能）。

**我的判断：除非你打算长期投入做跨平台或富交互，否则这条路是净亏损。** 你要的是"把界面做对"，不是"换技术栈"。

## 四、我要质疑的地方

### 4.1 "五版视觉方案"这件事，投入产出比可能不对

你在第一轮要了五个方向的完整原型，然后选了 BLACKSITE 并只微调。这说明**方向探索阶段其实一个方案就够了**——你心里已经有明确的审美取向（深色、紧凑、技术感）。

真正消耗时间的是后面的细节对齐（01–08 逐个过、弹窗族、两条流程）。这部分做得非常扎实，是对的。

**建议**：以后不要再做多方案对比。直接给一版，在细节上快速迭代。

### 4.2 更值得先解决的问题：这套界面到底服务谁

我做完 demo 后发现一个更根本的问题——**这个应用的核心价值不是"好看"，是"让用户知道哪个 mod 现在生效、为什么不生效"。**

你的实际使用场景大概是：
- 装了几十个到几百个 mod
- Steam 创意工坊自动同步，`addons/` 和 `addons/workshop/` 两套目录
- 同一个人物只能穿一套外观（互斥）
- 游戏内菜单和 addonlist.txt 可能不同步

现有代码已经解决了这些（`adopt_all`、`mutex`、`sync_enabled_from_addonlist`）。但**界面没有把"冲突"讲清楚**。

我们在 03 讨论时把"冲突与容量"删掉了，理由是 `set_enabled(mutex=True)` 已经自动处理。这个理由成立，但代价是：**用户看不到"为什么我装了 6 个 Ellis 皮肤只有 1 个生效"**。

我的建议：在 Inspector 的"同组"里，把当前组的状态直接写出来——

```
同组  1 / 6 生效
● 夏日甜点屋          ← 生效中
○ Koharu
○ VRC lime
○ 藤田
（其余 2 个折叠）
```

这个改动比任何视觉打磨都更能减少用户的困惑，而且几乎零成本（数据已在 `MUTEX_CATS` + `set_enabled` 里）。

### 4.3 被忽略的点：首次使用

现在所有设计都假设"库里已经有 mod"。查了代码，这块几乎是空白：

- `_intro_shown`（main_window.py:863）只控制一个 220ms 淡入动画，不是引导。
- `_render_empty()`（main_window.py:1275）就一行 `QLabel(text)`，居中显示"未配置游戏目录"或"没有匹配"。
- 没有"开始使用"页面，没有目录检测失败后的补救路径。

真实首启路径大概是：装好 exe → 打开 → 空白网格 → 不知道要先设游戏目录 → 卡住。

这比视觉打磨更影响可用性，而且与"砍掉提示文字"的原则**不冲突**——引导不是贴在界面上的说明，是**独立的一屏**，用完就消失：

```
┌─────────────────────────────────┐
│                                 │
│   没有找到 Left 4 Dead 2         │
│                                 │
│   ┌───────────┐ ┌───────────┐   │
│   │ 自动检测   │ │ 手动选择   │   │
│   └───────────┘ └───────────┘   │
│                                 │
└─────────────────────────────────┘
```

检测成功后直接进入主界面，不出现第二屏。

### 4.4 「不做批量选择」这个决定，我建议重新考虑

你之前说 ActionBar 四项就够、不做批量。我照做了。但考虑真实场景：

- 一次导入 20 个 mod，导错了想全删
- 想一次性停用某几类

现在的替代方案是"逐张卡片双击"。20 个就要点 40 次。

不过——**如果导入流程本身就能让用户在写入前取消勾选**（已经做了），那批量删除确实不常发生。所以我倾向维持现状，但如果你实际用起来觉得烦，这是第一个该加回来的。

### 4.5 关于"其他配色方案暂时搁置"

合理。但要注意：`tokens.css` 里的四套色板如果一直不用，会成为死代码，后面容易忘记维护。

建议明确一件事：**这四套色板是"未来可能做主题切换"还是"只是设计探索的存档"？** 如果是后者，应该从产品代码里移出去，放到 `docs/` 里存档，别留在 `tokens.css`。

## 五、我的推荐

**路线 B（PySide6 + QtWebEngine）**，但分三步走，每一步都可回退：

### 第一步：先做壳，验证风险（1–2 天）

不迁移任何功能，只做：
- `QWebEngineView` 加载本地 `demo.html`
- `QWebChannel` 暴露 `getMods()` / `toggleMod()` 两个方法
- 无边框窗口 + 窗口控制按钮 + 拖动标题栏
- PyInstaller 打包，**实测分发体积与冷启动时间**

**这一步的目的不是出成果，是拿到两个数字：体积多少、启动多慢。** 如果体积从 40 MB 涨到 240 MB 你不能接受，立刻止损转 A 路线，只损失两天。

### 第二步：迁移主界面（3–5 天）

- `demo.html/css/js` 接真实数据
- 网格用虚拟滚动或分批渲染
- 保留现有 `workers.py` 的 QThread，通过 signal → channel 推送进度

### 第三步：迁移弹窗与设置页（2–3 天）

- 弹窗已在 `states.html` 定稿，直接转成组件
- 设置页同理

### 可回退性

第一步验证通过后再走第二步。如果第二步遇到 WebEngine 无法解决的问题（例如中文输入法在某个 Windows 版本异常、或客户环境禁用 GPU），因为业务逻辑从未改动，回退成本仍然只有已迁移的 UI 部分。

## 六、需要你拍板的

1. **分发体积能接受多大？** 这是选 A 还是 B 的唯一硬指标。如果你要求 < 80 MB，只能选 A。
2. **你的用户是不是只有你自己？** 如果只有你，体积和启动时间都不重要，直接选 B。
3. **4.2 的"同组状态可视化"要不要加？** 我认为这是比任何视觉细节都更值得做的一件事。
4. **4.5 的四套色板，是存档还是产品特性？**
5. **4.4 的批量选择，确认维持"不做"？**
